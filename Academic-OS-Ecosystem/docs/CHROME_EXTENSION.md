# Chrome Extension: Build, Configure, Deploy

The tracker in `frontend/` is packaged as a Manifest V3 Chrome extension.
This page covers building it, the settings it needs, and the security
properties it is built to keep.

## What the extension does and does not do

- It opens the tracker in a browser tab from the toolbar button (`extension/background.js`).
- It requests one permission, `identity`, used for Google sign-in.
- It calls the Academic OS backend. Lumen is connected through the backend's
  OAuth flow, so the extension never sees Lumen credentials.
- It does **not** read Lumen pages, inject scripts into them, intercept network
  traffic, or capture tokens.
- Its CSP is `script-src 'self'`. All scripts are local files. Third-party
  libraries (Firebase, Chart.js, html2canvas) are vendored in `frontend/vendor/`
  at pinned versions.
- The admin dashboard is shown only to the verified admin account. The backend
  enforces this on every request. See "Access control" below.

## 1. Build

```bash
python scripts/build_extension.py \
  --api-url https://<your-backend-host> \
  --google-client-id <client-id>.apps.googleusercontent.com
```

The output goes to `extension/dist/`. The build fails if any page contains an
inline `<script>`, a remote `<script src>`, an inline `on*=` handler, or
`eval`, because Chrome would block those at runtime.

Load it with `chrome://extensions` → Developer mode → **Load unpacked** →
select `extension/dist`.

## 2. Extension ID

Chrome derives an unpacked extension's ID from its folder path. For a stable ID
across machines, either pin a `key` in the manifest, or publish to the Chrome
Web Store, which assigns a fixed ID. The ID is needed for steps 3 and 4.

## 3. Google OAuth client (sign-in)

`chrome.identity.launchWebAuthFlow` runs Google's OAuth implicit flow and returns
an ID token, which Firebase then accepts. Set this up in Google Cloud Console:

1. Create an OAuth client ID of type **Web application**. (The current docs
   should be checked for the exact client type that `launchWebAuthFlow` needs
   with the `id_token` response type. This has not been tested against Google.)
2. Add this authorised redirect URI, using your extension ID:
   `https://<extension-id>.chromiumapp.org/`
   (`chrome.identity.getRedirectURL()` returns this value at runtime.)
3. Restrict the consent screen to the BITS Workspace domain
   (`bitspilani-digital.edu.in`). The build also sends `hd=` as a hint, but the
   backend and the client both enforce the domain.
4. Pass the client ID to `--google-client-id` (step 1). It is a public
   identifier, not a secret.

## 4. Backend configuration

Set these on the backend host:

| Variable | Value | Why |
|---|---|---|
| `CHROME_EXTENSION_ORIGINS` | `chrome-extension://<extension-id>` | Allows the extension's origin through CORS. Only listed IDs are accepted. |
| `FRONTEND_URL` | `chrome-extension://<extension-id>/index.html` | Where the Lumen OAuth callback returns the student. |
| `LUMEN_REDIRECT_URI` | Backend callback URL (unchanged) | Must match the Brightspace app registration. |
| `ADMIN_DASHBOARD_EMAIL` | `2025em1300265@bitspilani-digital.edu.in` | The only account that can view the admin dashboard. |

After changing these, restart the backend.

## 5. Access control

| Data | Who can read it | Enforced by |
|---|---|---|
| Own tracker progress, Lumen activity, profile, prediction | The student | `_require_firebase_user` / `_require_authenticated_student` compare the Firebase `sub` to the requested student ID |
| All students' progress, Lumen data, profiles, predictions (`/api/admin/dashboard/progress`) | `ADMIN_DASHBOARD_EMAIL` only | `require_admin_claims` verifies the Firebase RS256 signature, audience, issuer, expiry, `email_verified=true`, and the exact email |
| Lumen OAuth tokens | Nobody in the browser | Encrypted at rest on the server (Fernet). Never returned in any response. |

The frontend check in `js/dashboard.js` only controls what is displayed. It is
not a security boundary. Anyone can edit a browser's JavaScript, so the real
gate is the backend check above.

## 6. Prediction model

- Endpoint: `GET /api/students/me/insights`. Updated by `GET /api/lumen/progress`
  and `PUT /api/students/me/profile`.
- Inputs come from three sources, and each input is labelled with its source:
  Lumen activity, the student's self-reported profile, or the training median
  (`model_artifacts/feature_defaults.json`, regenerated by
  `scripts/build_feature_defaults.py`).
- The model is trained on synthetic data and has **not been validated on real
  placement outcomes**. Every response includes this disclaimer. Do not use the
  estimate for real decisions until it is validated.

## 7. Retiring the old extension

The older extension in `../Academic-OS-Chrome-Etension/` fetches Lumen pages
with the student's own session cookie and posts the results to the backend. The
new build does not need that and should replace it. Remove it from student
machines once the new extension is working.

## Verification performed

- Backend and integration tests: `pytest tests/unit tests/integration` (41 tests).
- Built extension loaded in a Chromium-based browser with its real CSP: Firebase
  and Chart.js load, and there are no console errors.
- Prediction card rendered for the ready, awaiting-Lumen, and insufficient-data
  states, and injected HTML is escaped.

Not verified here: a live Lumen tenant, a live Google sign-in through
`chrome.identity`, and Firebase sign-in in a real session. These need a manual
check with real accounts.
